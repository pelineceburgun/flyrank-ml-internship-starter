FLYRANK ML INTERNSHIP — CAPSTONE — LANE 2

Which pages should a content reviewer look at first?

Ranking refresh priority from observed search performance — a rule baseline, a leakage audit, and a client-grouped honest evaluation of Random Forest against it.

Author — Pelin Ece Burgun Date — August 2026 Repo — github.com/pelineceburgun/flyrank-ml-internship-starter
01

Abstract

This is FlyRank's own content problem: across its client portfolios, content teams manage far more live pages than they have review capacity for, so the question this work answers is the one FlyRank's reviewers actually face — on any given cycle, which existing pages are most worth a human look for a possible refresh? Using FlyRank's anonymized starter export — 30,000 pseudonymized content items across 32 clients, each described by trailing-90-day search and engagement metrics — I built a transparent rule baseline (stale-but-still-visible) and compared it against Logistic Regression, a Decision Tree, and a Random Forest, all scored on a client-grouped held-out split so no model is credited for memorizing a client it already trained on. After catching and removing two columns that were the label in disguise, Random Forest reached 0.670 average precision against a 0.391 held-out base rate — a real, non-trivial lift over both the base rate and the rule, which itself failed to clear the base rate on the honest split. The result is packaged as a ranked, reason-coded review queue with a documented failure pattern and an explicit no-go list, meant to support a reviewer's triage decision — not to replace it.

02

Introduction / Problem statement

FlyRank runs search-performance monitoring for many client content portfolios at once, and that scale is exactly where this problem shows up: a content strategist responsible for several client portfolios is looking at a spreadsheet of thousands of live pages with no principled way to decide which ones to open first this week. Some pages are quietly losing visibility; most are fine. Review time is the scarce resource, so the real decision isn't "is this page declining?" in the abstract — it's "given limited capacity, which pages go to the top of the queue?" This paper is a case study in answering that question for one lane of FlyRank's own product surface — content refresh prioritization — using only anonymized, public-safe performance data.

Getting this wrong has a cost in both directions. Flagging a page that didn't need attention burns review time and possibly content-production budget on a false alarm. Missing a page that's genuinely losing ground lets that decline run unnoticed for another cycle. A fixed rule (e.g., "anything untouched for 90+ days") is easy to explain but blunt — it can't weigh exposure, position, click-through, and freshness together the way an experienced reviewer does by eye. That combination of several tangled, non-obvious signals is exactly the situation where a learned ranking has room to beat a hand-written rule — if, and only if, it's evaluated honestly enough to trust the size of that improvement.

03

Data

The FlyRank internship provides two data surfaces: a full ~79M-row daily warehouse release on Hugging Face (FlyRank/internship-warehouse, build flyrank_pseudonymized_warehouse_release_v20260703, daily facts spanning January 2025 – June 2026) queried via DuckDB, and a small anonymized starter export shipped directly in the repo. I used the warehouse's March 2026 partition early on to write and verify a data contract (grain, row counts, missing-value windows), but the model, baseline, and review queue in this paper are all built and evaluated on the 30,000-row starter export (data/raw/content_refresh_anonymized.csv, 32 clients, 44 columns) — a scope decision the internship's own lane guide names explicitly as valid for this lane, alongside the caveat that a starter-slice result "is not a benchmark on the full ~79M-row daily warehouse."

Stated plainly: every number in this paper's Results section comes from the 30,000-row anonymized starter slice, not the full warehouse. Treat this as a result on one portfolio snapshot, not a warehouse-scale benchmark — a natural next iteration would re-run the same validated pipeline against the warehouse's daily facts and see whether the finding holds at scale.

Unit of analysis: one row is one pseudonymized content item, summarized over its trailing 90 days (search impressions/clicks/position, sessions, click-through rate, engagement/scroll rate, content age, and freshness). Excluded, deliberately and always: client names, domains, URLs, page titles, and raw search queries — the starter export ships without any of these. content_id and client_id are hashed pseudonyms, used only to group the train/test split and never as model features. Two rate columns worth flagging for anyone re-reading the raw data: ctr/trend_pct and similar are already on a 0–100 percentage scale (ctr = 0.76 means 0.76%, not 76%), and avg_position == 0 means "no data," not literal rank zero.

04

Methodology

Label

is_declining_label = (trend_direction == "down"), a current-window bucket derived upstream by FlyRank's own pipeline rather than a future-observed outcome I measured myself — a deliberate, named limitation of this beginner-scope proxy (see Limitations). Overall label rate on the full 30,000-row slice is 0.542.

The leakage catch that shaped the feature set

Two columns that look like ordinary engagement metrics — impressions_last_30d and impressions_prev_30d — turned out to be the label in disguise: trend_pct correlates 0.9999999984 with the exact arithmetic difference between them. Including them made every model hit precision@50 = 1.000, a "suspiciously perfect" number that was the tell. Both columns were dropped from the feature set below; a confession test (re-adding them) lifted Random Forest's average precision from 0.670 to about 0.90 and confirmed the diagnosis. The final feature set keeps related-but-not-formula columns like clicks_last_30d and sessions_last_30d, which correlate with the outcome without being the formula that defines it.

Baseline

A transparent, no-fitted-weights rule: a page enters the review queue if it is stale (days_since_last_update ≥ 90) and visible (impressions_last_30d ≥ 500, chosen over the product's own "search volume" quick-win signal after a signal check showed search volume doesn't reliably predict real traffic here). Staleness alone or visibility alone isn't a reason to review; the combination is meant to capture "an old page still worth someone's attention."

Validation design

Client-grouped split, not a random row split: 6 of 32 clients (about 19%) held out entirely, none of their rows seen in training, random_state=42 throughout for reproducibility. This matters because client_id must define the split or a model can learn "this client's typical traffic level" instead of a transferable "which pages look like they're losing ground" pattern — and in production this model would score new clients' content, not more pages from clients it already trained on. Re-running the identical pipeline on a naive random row split confirmed the risk directly: average precision was inflated by 0.10–0.12 points for every learned model, and even the base rate itself shifted (0.542 on the random split's test rows vs. 0.391 on the client-grouped holdout), because a random split mixes easy and hard clients evenly while an honest client holdout can land on a structurally different subset.

Models compared

Logistic Regression (readable baseline-of-a-model), a depth-limited Decision Tree, and Random Forest (n_estimators=300, max_depth=8, min_samples_leaf=20, class_weight='balanced') — all three inspectable at some level, which mattered given this queue needs to be explainable to a non-technical reviewer. Gradient boosting was deliberately not tried: Random Forest already cleared the baseline by a wide, stable margin, so adding that complexity wasn't earned by the comparison.

What the model leans on. Permutation importance on the winning Random Forest is led by days_with_impressions, impressions_90d, clicks_last_30d, sessions_last_30d, and avg_position — persistence and volume of exposure, recent click activity, and search rank, which is exactly what a strategist would look at by hand. None of them is the excluded label-adjacent pair, which is itself a sanity check that the leakage catch above worked.

Where it's wrong. In the audited top-50 held-out ranking, 7 of 50 flagged pages were not actually declining — and every one of those misses shared the same pattern: updated in the last ~20 days, trending up or stable. The model appears to be reading sustained high visibility and a good position as a general decline-risk signal, even for pages that haven't started reverting yet. That's a real, named limitation, not a footnote — a model_decline_risk flag should read as "worth a look," not "confirmed declining," especially for recently-updated pages.

A note on the two base rates in this section: 0.391 is the held-out client-grouped base rate — the number that belongs next to any out-of-sample claim. 0.542 is the in-sample base rate across the full 30,000-row portfolio, used only for the archetype/decay sanity checks above, where the queue is scored on all 32 clients (including ones the model trained on) so every row gets an action. Conflating the two would overstate how well the model generalizes — they're kept separate throughout.
06

Limitations & honest framing

  • Cross-sectional, not causal. Every result comes from one snapshot period on one anonymized slice. Nothing here tests whether refreshing a flagged page actually improves its trajectory — that needs a before/after design this dataset doesn't provide. The honest claim is "worth reviewing," never "will improve if refreshed."
  • A defined proxy label, not a measured future outcome. is_declining_label is a current-window bucket computed by an upstream rule, not something observed by watching a future window unfold — a known limitation of this beginner-scope target, named at framing time rather than discovered later.
  • A specific, named error pattern. 7 of the top-50 held-out flags were false alarms, all recently-updated pages trending up or stable. This doesn't generalize cleanly to the full needs_recency_check segment (its decline rate, 51.1%, sits close to the overall base rate) — so recency is kept as a human-review prompt, not a hard exclusion rule.
  • The decay signal is not monotonic. It climbs with staleness through 180 days, then reverses in the smallest, noisiest bucket (181+ days, n=174 of 30,000) — not trusted past that point.
  • One portfolio, not a universe. 32 clients, one anonymized export. A client whose vertical, CMS, or content strategy looks very different from this portfolio is untested territory for this model.
  • Not the full warehouse. Built and validated on the 30,000-row starter slice, not FlyRank's ~79M-row daily release — see Data. A warehouse-scale re-validation is the natural next step, not a claim this paper makes.

The claim this paper is willing to defend: on content held out by client — clients the model never trained on — Random Forest ranks pages by measured decline risk with average precision 0.670 against a base rate of 0.391 on that same held-out slice — a real, directional improvement over guessing, not a guarantee for any single page. The honest use is decision-support: a "worth a look" queue for reviewers, cross-checked against recent update date, not an automatic "confirmed declining" verdict.

Ranked recommendations

A reviewer with limited time, in order:

  1. 1

    Work the refresh-priority queue first n=4,204

    Watchlist Decliner + Stale Heavyweight archetypes, sorted by model probability descending. This is where the audited model signal and the stale-but-visible rule most often agree — the highest-confidence, cheapest-to-defend group.

  2. 2

    Then review_ctr n=4,658

    CTR Underperformer — good exposure, weak click-through. This is usually a snippet/title problem, not a content-decay problem — different fix, same queue.

  3. 3

    Then review_position n=2,400

    Buried but Wanted — real search demand, weak ranking position. A visibility problem, worth a different kind of editorial attention than a refresh.

  4. 4

    Leave no_action alone — for now n=18,738

    Steady Performer. Not flagged today does not mean safe to ignore forever or a candidate for pruning — it means nothing in this cycle's signals crossed a threshold.

Before acting on any flagged row, a human checks:

  1. Is it evergreen/reference content on purpose? A stable page that isn't supposed to change looks identical to a stagnant one in this data.
  2. Is the decline seasonal? A yearly-cycle topic dipping on schedule isn't decay, and a refresh won't fix a calendar.
  3. Is the drop a SERP-feature problem (snippet/AI overview stealing the click) rather than a content problem? That's a different fix entirely.
  4. Was this page updated very recently? Not because the model is usually wrong there — it isn't, broadly — but re-queuing a page an editor touched three weeks ago spends capacity that's better spent elsewhere without a specific reason.
  5. Is a refresh already scheduled for this page? Avoid a duplicate flag wasting a second reviewer's time.

What should never be automated from this queue

  • No auto-publishing — this system produces a reviewed list; a person decides and a person makes the change.
  • No auto-archiving or deprioritizing from a low score alone — "not flagged today" is not "safe to remove."
  • No client-facing performance guarantees built on this queue — "refresh X and traffic will grow" is exactly the causal claim the evidence here can't carry.
  • No scoring a new client's content with this exact model without re-validation — this is a portfolio-specific result, not a universal one.
  • No treating confidence: high as certain — it means two independent signals agree, not that the outcome is guaranteed.

Reproducibility

Every number in this paper traces to a notebook in the repo, run with random_state=42 throughout. Rerun from a fresh clone:

# clone and install
git clone https://github.com/pelineceburgun/flyrank-ml-internship-starter
cd flyrank-ml-internship-starter
pip install -r requirements.txt

# notebooks run top to bottom, in order — see work/notebooks/

The seven weekly notebooks this paper is built from, plus the consolidated capstone notebook:

w01 — research question w02 — ML task framing w03 — data contract w04 — baseline score w05 — model + split w06 — validation audit w07 — action playbook capstone — consolidated

Data: data/raw/content_refresh_anonymized.csv (committed, anonymized starter slice — see DATA_USE.md for the public-safety rules this repo follows). The full ranked queue (work/outputs/action_playbook_queue.csv) is gitignored and regenerated deterministically on rerun; the metrics receipts (work/outputs/action_playbook_metrics.json) and figures in this paper are committed so every number above can be checked directly against the file that produced it.
